> 括号里是提示，不要念出来。正文约 1100 字，按每分钟 220 字算正好 5 分钟。

## 0:00–0:40　一句话说清我们干了什么

（先给结论，别铺垫。）

我们没有复述 CLI-Anything 的论文，我们**给它补了它自己没有的那个数字**。

论文说 CLI 比 GUI 更适合 agent，但通篇没有一个任务成功率——技术报告把 benchmark 列为
"下一步"，README 的 Roadmap 里那条至今没勾。我们把它变成可执行的实验：同一批第三方桌面
任务、同一个模型、同一个预算，四种接口各跑一遍，用 OSWorld 的原始判分函数打分。

## 0:40–1:40　任务集：143 里筛出 133

（这页讲"我们没有挑软柿子"。）

任务全部来自 OSWorld 的 GIMP 与 LibreOffice 部分，固定提交 `5123bfdbbc`，只用任务描述、
输入文件和判分函数，不用它的虚拟机。

143 个里我们没有全用：有些离开虚拟机根本判不了分——6 个依赖 GIMP 配置或命令输出，2 个依赖
幻灯片音频或控件树，2 个依赖特殊参考数据。逐条列了原因，剩 **133 个**。

按软件分层、固定种子、**在看到任何结果之前冻结**：开发集 53，测试集 80。refine 只准看
开发集，这是后面所有结论的前提。

## 1:40–2:40　判分：把 OSWorld 的判分器搬到 Windows

（这页讲工程量，也讲两个真实的坑。）

36 个判分模块原样 vendor 进来，然后重写 `evaluate()` 的语义：`func` 可以是列表、`conj`
可以是 `or`、`and` 遇 0 短路、`or` 遇 1 短路；`infeasible` 只有最后一步是 FAIL 才给 1；
缺包就明确报 `grader_unavailable`，**绝不当 0 分混进成功率**。

两个坑。第一，**表格类任务不能直接判**：`openpyxl` 写的公式不带缓存值，而判分读的正是
缓存值，所以判分前要用无界面的 LibreOffice 重算——不重算，做对了也是 0 分。

第二，**标准答案本身不一定拿满分**。实测有 13 个任务的参考件自己就不到 1 分：有的是
"修改前"的参考件而不是"修改后"的目标，有的规则要求标题必须移动过，gold 对 gold 必然 0。
所以上限检查改成两步：先算 baseline，不到 1 的标成**不可判定**，不算 harness 的损失。
**这个不修，我们会把 OSWorld 自己的问题算到 harness 头上。**

## 2:40–3:40　上限检查现在能跑出什么

（诚实报数，包括分母。）

上限检查问的是：「照着标准答案做，这个接口能不能做对。」

133 个里：11 个不可行、15 个没参考件、13 个参考件自己不是不动点、3 个参考件是 PDF 或
截图这种渲染产物、21 个当天下载不到，**真正测到保真度的有 70 个**。分母能立起来是因为
把 LibreOffice 26.8 直接解包进项目目录（不写注册表、不进 Program Files），也装好了
`cli-anything-libreoffice`。

70 条测完：**12 条满分，58 条掉分，上限 17.1%**。抽查定位了几种机制：GIMP 那条是 harness
没有"把图片当作项目导入"的动词，属**表达力**；Calc 是**图表被丢掉**、**`0.00%` 格式退化成
`General`**、**公式写成 `=of:=B2-C2-…` 带前缀，重算后整列 `#VALUE!`**；Impress 19 条全丢，
因为导入导出**只保留文本框**，6 页每页 5–13 个图形，回来只剩 1–2 个文本框。

标准答案原样过一遍是 1.00，只有经 harness 导出才掉，所以不是我们管线的 bug。

## 3:40–4:30　接口对照：谁赢，为什么赢

（这页是新增的，也是最有说服力的一组。）

同一个模型 `auto/deepseek-v4.1-flash`、同样 50 次调用，我们让三条接口跑同一件事：

- **改文章标题**：自家 CLI **一条命令，9 次调用、1.3 万 token、17 秒**；GUI 在记事本里点了
  50 次，文件里还是 `title: "Welcome"`，得 0.5。
- **全文字体改 Times New Roman**：官方 harness 有 `style apply`，但一次只能作用一个段落，
  15 段就把预算用光，停在导出前，得 0；**GUI 全选改一次就成，得 1.0**。

两条单次试跑提示：批量操作与精确文本接口会影响结果，暂时不能推出总体胜负。
GUI 累计 token 更高，可能同时来自截图与重复控件树；图片字节数不能直接换算 token。

顺带说交付状态：**113 个测试全绿**，六个子命令齐备，GUI 臂不是摆设——截图真的以图片形式
进了模型上下文（原来是个真 bug：截图被当文本占位符丢掉，模型全程盲操作）。

## 附：可能被问到的问题

**Q：为什么不用 OSWorld 的虚拟机，省事不好吗？**
A：因为研究问题 1 是"harness 对裸脚本"。裸脚本臂需要在本机直接跑 Python 和
`soffice --headless`，虚拟机里反而绕。而且 GUI 臂要的是 Windows 原生控件树，
OSWorld 的 Ubuntu 虚拟机给不了。

**Q：133 个任务够不够？**
A：不够到能分辨 10 个百分点的差别，够到能分辨 30 个百分点。这个我们写进报告，
不装作够。

**Q：上限检查的可测任务从 2 个变成 70 个，是怎么做到的？**
A：把 LibreOffice 解包到项目目录、装上 LibreOffice 的 harness。原来卡住的两类任务
因此解锁：需要重算公式缓存的表格任务，和需要 `cli-anything-libreoffice` 的
LibreOffice 任务。

**Q：refine 会不会过拟合？**
A：协议上做了三道锁：refine 只看开发集；测试集失败分类放到最后一轮 refine 之后
才做；同时报开发集和测试集成功率，差距就是过拟合的度量。

**Q：为什么还要测你们自己的 CLI？**
A：因为只测别人的 harness，结论只对别人的代码成立。自家 blog CLI 是可复现的最小
样本，而且它和官方 harness 在两条任务上正好互相赢一次——CLI 赢在精确文本编辑，
harness 和 GUI 赢在批量操作。这条赛道的判分只读文件（front matter 和 `public/`
产物），不读 CLI 的输出，所以不会出现「CLI 说做完了就给分」。

**Q：GUI 臂真的能跑吗，还是只是接上了？**
A：实测过：Windows-MCP 六秒起来，工具表被白名单削到 9 个，一次截图返回 1.4–2.9 MB
的 PNG，并且以图片形式进了模型上下文。这里原来有两个真 bug——截图被当成文本占位符
丢掉，模型全程盲操作；MCP 会话绑在创建它的事件循环上，每次调用新起一个循环会让第二次
调用直接失效。两个都修了才有现在的 GUI 臂。而且它真的赢过一局：全文字体那次 GUI 拿
满分、官方 harness 拿 0。
