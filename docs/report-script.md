## 0:00–0:40　一句话说清我们干了什么

（先给结论，别铺垫。）

我们没有复述 CLI-Anything 的论文，我们**给它补了它自己没有的那个数字**。

论文说 CLI 比 GUI 更适合 agent，但通篇没有一个任务成功率。它的技术报告第 7 节把
benchmark 列为"下一步"，README 的 Roadmap 里"agent 任务完成率基准"至今没勾。

我们把这句话变成了可执行的实验：同一批第三方桌面任务，同一个模型，同一个预算，
四种接口各跑一遍，用 OSWorld 的原始判分函数打分。**四种接口里最关键的一组对照，
是 harness 对裸脚本**——因为如果写脚本也一样能做，那 harness 的价值就不在"能做"，
只在"少写代码"。

## 0:40–1:40　任务集：143 里筛出 133

（这页讲"我们没有挑软柿子"。）

任务全部来自 OSWorld 的 GIMP 和 LibreOffice 部分，固定提交 `5123bfdbbc`，只用任务
描述、输入文件和判分函数，不用它的虚拟机。

一共 143 个。我们**没有全用**，因为有些任务离开 OSWorld 的虚拟机根本判不了分：
比如有 6 个 GIMP 任务判的是 GIMP 自己的配置文件，有 2 个判幻灯片里的音频，还有 2 个
判的是只有 VM 里才有的本地参考文件。这些逐个列了原因，剩 **133 个**。

按软件分层、固定随机种子、在看到任何结果之前冻结：**开发集 53，测试集 80**。

这个划分是后面所有结论的前提——refine 只准看开发集，测试集留到最后。

## 1:40–2:40　判分：我们把 OSWorld 的判分器搬到了 Windows

（这页讲工程量，也讲一个真实的坑。）

OSWorld 的判分函数跑在 Linux 虚拟机里，我们要它在 Windows 上、没有虚拟机的情况下
跑出一样的结果。做法是把它 36 个判分模块原样 vendor 进来，然后**重写它的
`evaluate()` 语义**：

- `func` 可以是列表，`conj` 可以是 `or`，`and` 遇到 0 短路、`or` 遇到 1 短路；
- `infeasible` 任务只有在 agent 最后一步是 FAIL 时才给 1 分；
- 结果文件不存在给 0 分，和上游一致；
- 缺第三方包就明确报 `grader_unavailable`，**绝不当成 0 分混进成功率**。

两个具体的坑，值得说：

第一，**表格类任务不能直接判**。`openpyxl` 写的公式不带缓存值，而 OSWorld 的
`compare_table` 读的正是缓存值。所以每次判分前要用无界面的 LibreOffice 重算一遍。
不重算，agent 做对了也是 0 分。

第二，**标准答案本身不一定拿满分**。我们本来打算"把标准答案原样跑一遍，拿不到 1 分
就说明接口有损失"。实测发现有 13 个任务的标准答案自己就拿不到 1 分——有的是
"修改前"的参考件而不是"修改后"的目标，有的判分规则要求标题必须移动过，gold 对 gold
必然 0。所以我们把上限检查改成两步：先算 baseline，baseline 不到 1 的任务标成
**不可判定**，不计入 harness 的损失。**这个数字如果不修，我们会把 OSWorld 自己的
问题算到 harness 头上。**

## 2:40–3:40　上限检查现在能跑出什么

（诚实报数，包括分母。）

上限检查问的是：「如果 agent 完全照着标准答案做，这个接口能不能把事情做对。」

133 个采用任务里，11 个是不可行任务、15 个没有参考件、13 个的参考件自己就不是不动点，
3 个的参考件是 PDF 或截图这种渲染产物、21 个当天参考件下载不到，**真正测到 harness
保真度的有 70 个**。这个分母能立起来，是因为我们把 **LibreOffice 26.8 直接解包进项目
目录**（不写注册表、不进 Program Files），也装好了 `cli-anything-libreoffice`——所以表格
任务的公式缓存能被重算，上限检查也不再被「harness 没装」卡住。

70 条测完：**12 条往返后仍是满分，58 条掉分，上限 17.1%**。掉分不是判分噪声，每条都
查到了机制：

- GIMP 侧丢失那条是「把狗的抠图叠到背景上」——harness 没有「把一张图片当作项目导入」
  这个动词，属**表达力**缺陷；
- Calc 侧：**图表被导出丢掉**（gold 2 个 chart，导出 0 个）、**`0.00%` 数字格式退化成
  `General`**、**公式被写成 `=of:=B2-C2-...` 带 OpenFormula 前缀，重算后整列 `#VALUE!`**；
- Impress 侧 19 条可判定全部丢失，原因单一而彻底：导入/导出模型**只保留文本框**，
  6 页、每页 5–13 个图形和组合，导出后每页只剩 1–2 个文本框。

这三类都是**保真度**缺陷。我把标准答案原样过一遍是 1.00，只有经过 harness 导出才掉，
所以不是我们自己管线的 bug。这些正好是研究问题 2 要区分开的两类失败，而且都能点名
具体机制。

全部 133 条的汇总由 `roundtrip` 一条命令产出，报告里每一行都写分母。

## 3:40–4:30　代码已经就位，缺的是环境和模型

（这页讲交付状态。）

现在交付的是一套能跑的 runner，不是一份 PPT：

- `doctor` 一条命令告诉你缺什么；
- `tasks --excluded` 把 10 条排除连原因打出来；
- `split` 冻结划分；
- `roundtrip` 跑上限检查；
- `run` 驱动 agent 并判分，每次运行落一个目录：`record.json` 记分数和成本，
  `transcript.json` 记完整轨迹，`postconfig.json` 记哪些判分前置步骤跑了、哪些跳了；
- `report` 出主结果表、失败分类表、McNemar 配对检验和 refine 曲线。

**96 个测试全绿**，`run --dry-run` 不用花一个 token 就能验证
「下载→路径改写→重算→判分」这条链是通的。

四种接口也都接好了：harness 只能调 CLI，脚本臂有 shell 和 Python，GUI 臂走
Windows-MCP 且**工具白名单是硬约束**——如果 MCP 暴露了 `WriteFile`，我们也拒绝，
因为能写脚本的 agent 就不再是 GUI agent 了。

## 附：可能被问到的问题

**Q：为什么不用 OSWorld 的虚拟机，省事不好吗？**
A：因为研究问题 1 是"harness 对裸脚本"。裸脚本臂需要在本机直接跑 Python 和
`soffice --headless`，虚拟机里反而绕。而且 GUI 臂要的是 Windows 原生控件树，
OSWorld 的 Ubuntu 虚拟机给不了。

**Q：133 个任务够不够？**
A：不够到能分辨 10 个百分点的差别，够到能分辨 30 个百分点。这个我们写进报告，
不装作够。

**Q：上限检查的可测任务从 2 个变成 70 个，是怎么做到的？**
A：把 LibreOffice 解包到项目目录、装上 LibreOffice 的 harness。原来卡住的两类任务
因此解锁：需要重算公式缓存的表格任务，和需要 `cli-anything-libreoffice` 的
LibreOffice 任务。分母从 2 涨到 70，这一步的结论才真正有意义。

**Q：refine 会不会过拟合？**
A：协议上做了三道锁：refine 只看开发集；测试集失败分类放到最后一轮 refine 之后
才做；同时报开发集和测试集成功率，差距就是过拟合的度量。
